# AGY SDK GitHub Action

`run-agy-sdk` is a composite GitHub Action demonstrating how to run the Antigravity Python SDK (`google-antigravity`) for automated code reviews and task execution. Because it is a composite action running directly on the host, it allows the SDK to spawn Docker-based MCP servers (such as `github-mcp-server`) directly on the host runner.

## ⚙️ Workflow Installation & Setup

To use `run-agy-sdk` in another repository, you need to configure a GitHub Actions workflow that references this action. Follow the instructions below to set up automated reviews or comment-based on-demand reviews.

### 1. Provision API Key Secrets

The Antigravity action requires a Google Gemini or Antigravity API key to authenticate language model interactions.

1. Generate your API key.
2. In your target repository, go to **Settings** > **Secrets and variables** > **Actions**.
3. Create a new Repository Secret named `ANTIGRAVITY_API_KEY` and paste your API key as the value.

### 2. Configure the GitHub Actions Workflow

Create a new file in your repository at `.github/workflows/antigravity-review.yml` and copy the configuration.

For a complete workflow template that supports both **Automated PR Auditing** (runs automatically on code updates) and **Comment-Triggered Reviews** (triggered via PR comments), please refer to the reference workflow in [antigravity-autonomous-review.yml](.github/workflows/antigravity-autonomous-review.yml).

## 📥 Interface Specification

### Inputs

| Input | Description | Required | Default |
| :--- | :--- | :---: | :--- |
| `api-key` | Google Gemini or Antigravity API authentication token. | **Yes** | — |
| `github-token` | Token used for pull request inspections and posting code review comments back. | No | `${{ github.token }}` |
| `mode` | Operational mode: `goal` (autonomous prompt solving), `one-shot` (one-off query), or `review` (code audit). | No | `goal` |
| `goal-prompt` | The instruction detailing what task the agent must solve. | No | — |
| `sandbox-profile` | Enable process-level containment (`"true"` / `"false"` or custom path). | No | `"true"` |
| `trust-workspace` | Explicitly trust the repository directory (`"true"` / `"false"`). Bypasses interactive checks. | No | `"false"` |
| `prompt` | The prompt or command to execute. | No | — |
| `upload_artifacts` | Whether to upload execution artifacts. | No | `"false"` |
| `workflow_name` | The GitHub workflow name, used for telemetry/logs. | No | `${{ github.workflow }}` |
| `github_pr_number` | The Pull Request number the SDK is operating on. | No | `${{ github.event.pull_request.number }}` |
| `github_issue_number` | The Issue number the SDK is operating on. | No | `${{ github.event.issue.number }}` |

### Outputs

| Output | Description |
| :--- | :--- |
| `response` | The final clean Markdown response generated by the Antigravity agent. |
| `stats` | A JSON-serialized metadata payload representing token counts, latencies, and execution turn statistics. |

## 🛡️ Security Hardening Reference Manual

When integrating autonomous agents (using the `google-antigravity` SDK) into continuous integration pipelines, safeguarding against **third-party supply-chain injection attacks** and **malicious repository prompt hacks** is paramount. Follow this hardening specification to build an impenetrable barrier:

### 1. Network Egress Containment (Proxy Controls)

By default, an autonomous agent running dependencies installation commands (e.g., `npm install` or `go get`) could trigger malicious pre-install scripts that attempt to exfiltrate environment secrets to an external server. 

> [!CAUTION]
> **Enforce Strict Egress Firewalls**
> Restrict the runner or container network egress utilizing a local HTTP forwarding proxy (like **Squid**) or runner firewall utilities (like **iptables** / **UFW**).

Configure egress rules to exclusively allow:
*   **Google Gemini API:** `generativelanguage.googleapis.com:443`
*   **GitHub API:** `api.github.com:443`
*   **Vetted Registry Mirrors:** Block standard internet fetch pipelines. Force resolutions through authenticated internal artifact repositories (e.g., Artifactory, Nexus).

### 2. Ephemeral Runner Environments

Never execute autonomous agent workflows on persistent self-hosted runners. 

*   **Use Ephemeral VM Runners:** Utilize official GitHub-hosted runners or configured ephemeral self-hosted virtual machines (using projects like ARC - Actions Runner Controller) that completely destroy the host VM immediately upon job completion.
*   **No Persistent File Caching:** If caching folders (like `~/.npm` or `~/.cache`) are shared across executions, a malicious dependency in an unvetted PR could inject persistent malware into the cache directory to hijack subsequent jobs.

### 3. Mitigating Workspace Trust Vulnerabilities (GHSA-wpqr-6v78-jr5g)

In April 2026, a critical remote code execution vulnerability (GHSA-wpqr-6v78-jr5g) was discovered due to unsafe workspace trust checks and YOLO-bypass combinations on untrusted repositories.

*   `run-agy-sdk` defaults `trust-workspace` to `"false"`.
*   If `trust-workspace` is `"false"`, the Action restricts command execution and file write tools, confining execution to **Read-Only Mode**.
*   Only set `trust-workspace: "true"` inside jobs that have passed **rigorous manual verification** or are triggered strictly by maintainers (via our gated `issue_comment` dispatch flow).
*   **Never** use `pull_request_target` triggers with `trust-workspace: "true"` unless you have checked out the base branch of the repository rather than the untrusted contributor's PR branch.

### 4. Least-Privilege GITHUB_TOKEN Permissions

Do not grant administrator or push capabilities to the GITHUB_TOKEN used by the action.

*   Configure job-level permissions explicitly to prevent credential leaks:
    ```yaml
    permissions:
      contents: read       # Block code modifications or commits
      pull-requests: write # Permit only publishing reviews
    ```

### 5. API Key Security & Workload Identity Federation

Avoid embedding long-lived Google Cloud or Gemini API keys inside GitHub secrets.

*   **Workload Identity Federation (WIF):** Best practice involves setting up WIF to exchange short-lived OIDC tokens generated by GitHub Actions for ephemeral Google Cloud service account credentials. This eliminates the risk of API key extraction.
